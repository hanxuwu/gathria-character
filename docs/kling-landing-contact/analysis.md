# 落地接跑的支撑脚诊断

选择：把候选的接跑补帧从 `88 → 89 → 107 → 108` 改为 **`88 → 107 → 108`**。保留原片和补绘的全部像素、24 FPS 及 700 px/s 审阅速度，仅去掉一次脚部几乎静止的重复恢复姿态。每次恢复缩短 41.667 ms。

这是根据第二版原始源帧做的只读诊断，基线源 SHA256 为 `7ad4a85358fc67acfde96e56c3b0040a01289e231b91731dd1055f7f84eae9e5`。没有重新生成、变形或移动图片像素。第三版若只改变源版本元数据，画面测量仍适用；实际运行时与换装导出的验证另行记录。

## 找到的问题

实际恢复序列是 `85 → 88 → 89 → 107 → 108 → Run48`。前面的 85、88、89 已经落地，脚在画面内几乎不动，而横向移动仍每帧前进 `700 / 24 = 29.167 px`。这两次连续恢复占去约 58 px 的地面相对位移，比最后两张补绘之间的差异更明显。

近侧脚在 107 开始抬起，远侧鞋继续承担支撑，随后接入 Run48/49。我们沿同一只远侧鞋的可见鞋尖检查，而没有把抬起的近侧鞋错误当作新的支撑脚。

| 源帧 | 可见远侧鞋尖 x | 远侧鞋底最低 y | 头顶 y |
| --- | ---: | ---: | ---: |
| 85 | 328 | 693 | 269 |
| 88 | 327 | 693 | 260 |
| 89 | 327 | 693 | 245 |
| 107 | 304 | 693 | 238 |
| 108 | 271 | 697 | 231 |
| Run48 | 259 | 698 | 231 |

这些坐标以 512×768 原图为单位。鞋子区域由人工辨识，再用 alpha >128 的轮廓计算；区域、阈值、逐帧数据和各路线的头部位移都保存在 [analysis.json](analysis.json)。鞋尖与最低轮廓不是恢复出的骨骼触地点，滚脚和鞋型变化也会影响它们。原片的近、远脚存在透视高度差，不能强行把两只鞋底拉到同一条水平线。

## 为什么保留 88，去掉 89

| 恢复路线（含两端） | 85→Run48 鞋尖世界坐标总漂移 | 单帧最大头顶上移 |
| --- | ---: | ---: |
| 85→88→89→107→108→48 | 76.833 px | 15 px |
| 85→107→108→48 | 18.500 px | 31 px |
| 85→89→107→108→48 | 47.667 px | 24 px |
| **85→88→107→108→48** | **47.667 px** | **22 px** |

同时去掉 88、89 虽然脚部指标更低，却让头部从深蹲直接抬高 31 px，并出现一次约 3.8 px 的头部轮廓中心世界坐标后退，容易换成新的头部突跳。保留 88 仍能保留初始回身动作，最大头顶变化为 22 px，比保留 89 的方案略小。

所选方案减少约 **29.167 px、38%** 的这段鞋尖总漂移，提前一帧接回跑步；它不是精确锁脚。88→107 的头顶上移仍比旧路线最大步长多 7 个原图像素，属于需要在正常速度和换装画面中验收的取舍。

## 剩余边界

- 原片的固定足部落地姿态仍与恒定向前移动存在冲突；只去掉一帧无法完全解决。
- 107、108 和 Run48 的鞋底高度、轮廓仍有变化。原生后续跑步也包含滚脚，因此不能只优化某一个鞋尖坐标就声称动作正确。
- 基础单次 Jump 的原始帧列、跑步播放速率和移动速度应保持不变。此次仅调整实验候选的 Jump→Run 恢复序列，旧候选保存文件继续使用旧配置。
